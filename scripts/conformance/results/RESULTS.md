## (b) Hash + JSON Schema baseline against the verifiers

The baseline accepts a vector when every document it declares validates against its committed JSON Schema (Ajv 2020-12, set up as in `verify.mjs`) and every digest it can recompute from the vector alone matches. Those are the digests the valid vectors of the same schema declare in the manifests (RFC 8785, python-json-v1 or file bytes), plus the embedded digests listed under (c) as checked by the baseline. It does not check digests that name files outside the vector, and it replays nothing. *Strict* reads JSON as `verify.mjs` does, rejecting duplicate keys. *JSON.parse* keeps the last of duplicate keys. Both reject NaN and Infinity; Python's `json.loads` accepts them by default. *Verifier rejects* counts exit codes other than 0; a run without an exit code counts as neither.

## (c) Single-leaf mutations

Every JSON leaf of every valid vector is changed once: integer +1, float +0.125 (x2 when |x| >= 1e6), string + `x`, boolean flipped, null to `x`. The edited record goes through its verifier; *detected* means an exit code other than 0.

- **Stale** leaves every digest as it was.
- **Resealed** recomputes every digest the verifier checks, as someone who edits a record and re-hashes it would. The embedded digests below come first, then the manifest's digests, innermost first. Each digest uses the canonical form the edited record's `schema_version` requires; which version uses which form is learned from the valid vectors, so an edit from decision-control record schema 3 to 4 is resealed in RFC 8785. In a directory vector, the SHA-256s in `provenance.json` come last.
- Resealing rewrites digests, not copies. An OPA input or a Cedar request repeats parts of the proposal, so an edit to a repeated field is caught by that comparison.
- Digest fields, declared or embedded, are not mutated. In directory vectors only JSON files in compact sorted form are mutated; JSONL files and `provenance.json` are not.

### What the mutation rates show, and what they do not

- Digests detect change, not forgery: whoever edits a record can recompute its hashes ([DECISION_RECORDS.md](../../../docs/DECISION_RECORDS.md#compatibility-and-limits)). A resealed edit is caught when replay recomputes something from the edited field, or finds that it no longer matches a copy elsewhere in the record.
- Fields no recomputation depends on stay bound only by a signature (`--require-signature`): free text such as review and event notes or question instructions, caller-supplied labels such as `recommendation.model`, `question_version`, `proposed_by` and `produced_by.version`, inputs whose edit leaves the recomputed verdict unchanged, and `schema_version` where the next version reads the same record and the edit is resealed in that version's canonical form. The lists above name them for this corpus.
- One edit per value type, one leaf at a time, on vectors written by the same authors as the verifiers. The rates describe this corpus and operator, not records in general or an adversary who edits several fields together.
