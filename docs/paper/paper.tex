\begin{abstract}
Signed receipts for agent actions already exist, and some of their verifiers
re-apply rules. We measure what recomputing the verdict adds over digest and
schema checks, and what it leaves unbound. A decision record keeps the inputs
and frozen rules of one go/no-go decision (a typed model answer, a
policy-gated agent action with human approval, an experiment promotion); its
verifier re-derives the verdict without running a model. On our own
conformance vectors and JSON Schemas, which tie no verdict to its inputs, of
4,214 single-leaf edits with every digest recomputed, the hash and schema
check rejects 1,104 (26.2\%) and the verifiers 3,466 (82.2\%); 735 pass
both. Only the verifiers reject 2,375 (56.4\%), 2,263 as mismatches; a
stricter schema would lower that share. Replay is a
consistency check: consistent edits of several fields pass, as do single
edits of labels, such as the model named in most proposed actions,
and of inputs that leave the verdict unchanged. All fixtures are synthetic;
no agent or model is run.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Model output is not authority; the approval that follows it is. Take the
exported record of an agent action awaiting human approval: proposal, frozen
policy, verdict and event history under a SHA-256 digest. Append an
\code{EXECUTED} event and a result, and recompute the digest: the file still
validates against its JSON Schema and its digest matches
(Appendix~\ref{app:manifest}). A verifier that recomputes the verdict and
walks the lifecycle rejects it with no key, but an editor who also writes an
approval by a listed reviewer passes. Replay is a consistency check: it shows
that the recorded verdict follows from the recorded inputs under the rules
of the schema version the record claims, not that the inputs are the
original ones. Whoever can rewrite every field and digest can write any
self-consistent record.

Recomputation therefore complements a signature. A signature says that a
key holder vouched for the bytes, not whether the signed record is coherent;
replay catches an edit or error that breaks a relation it recomputes or
compares, whoever makes it and whether or not they re-hash or re-sign. Signed agent receipts are
plentiful: more than ten 2026 Internet-Drafts and several
preprints define them
\citep[e.g.,][]{farley2026acta,sahu2026receipts,sharif2026aat,ardebili2026novafabric},
and some verifiers re-apply rules. One re-checks separation of duties
offline and compares policy digests \citep{schrock2026authorization};
AgentBound, the nearest
design to ours, replays the action against the reconstructed policy
\citep{kaul2026agentbound}. We did not find a measurement of how much
recomputing the verdict adds over digest and schema checks, or of what it
leaves unbound. On our own vectors, a hash check with our own JSON Schemas,
which tie no verdict to its inputs, rejects 26.2\% of single-leaf edits
with every digest recomputed, the verifiers 82.2\%.

A \emph{record} keeps the inputs and the frozen rules of one go/no-go
decision. \emph{Replay} is recomputing the deterministic part of that
decision from inputs frozen in the record; a \emph{verifier} replays a record
and compares the result with what it states. No verifier runs a model:
replay re-executes neither the model \citep{sharif2026aat} nor an agent run
\citep{ardebili2026novafabric}. A \emph{label} is a caller-written value no
verifier can re-derive.

We contribute (1) the apparatus: records and standard-library verifiers that
recompute the verdict at three decision points (Table~\ref{tab:points}), with
schemas and 185 conformance vectors; (2) a single-leaf mutation sweep in
which every edited record goes through a hash and JSON Schema baseline and
through the verifiers, with every field whose edits pass published; (3)
lessons for builders of such records; and (4) a stated boundary: what the
records do not bind for an LLM agent, and where receipts are ahead.

We reuse the envelope, canonical JSON, signing and offline verification; the
format is one more of many. Every model
answer, probability and proposal is a synthetic fixture: no model or agent
is called, and the software has one author and no outside user. Only version
0.1.0 of the packages is published; what we evaluate beyond it is
unreleased. Code and vectors: \repourl{}; the results name their source
commit and the code's tree ids (Appendix~\ref{app:trace}).

\section{Decision Records and Replay}
\label{sec:records}

Three independent Python packages write and verify these records
(Table~\ref{tab:points}). They use only the standard library and are not one
integrated runtime. Each ships JSON Schemas \citep{wright2022jsonschema} and
valid, tampered and invalid vectors with expected exit codes; a Node checker
by the same author, sharing no code with them, re-checks schemas and digests
only. The jev-decision package records answers of decision models such as
Jev \citep{almeida2026jev}, which answer bounded questions with typed answers
and probabilities; their calibration is studied elsewhere
\citep{deusser2026jev}.

The records follow five rules. (1) A record embeds the inputs that replay
needs and the rules as data; the logic that applies them is verifier code.
(2) A schema version selects one digest form, RFC 8785
\citep{rundgren2020jcs} in current versions or exact file bytes for a Jev
evaluation directory, and one set of replay rules. (3) To verify is to
recompute the verdict, not only to compare hashes. (4) Exit code \code{1}
means that the evidence disagrees, \code{2} that the input is invalid or a
required check could not run. (5) Limits appear in the output:
\code{digest-only} for a frozen external policy that was not re-evaluated,
and \code{UNGATED}, never \code{PASS}, for an evaluation of labeled cases
without requirements.

Signing is optional and reused: an in-toto Statement
\citep{intoto2026statement} in a DSSE envelope \citep{dsse2024spec} over the
SHA-256 of the record file's exact bytes. The packages compute an HMAC tag
over Statement v1; an external \code{cosign} makes a Sigstore bundle
\citep{newman2022sigstore}, with Statement v0.1. Verifiers ignore both unless \code{--require-signature} is
given. Every holder of an HMAC key, each verifier included, can make a tag,
so it names no one; a Sigstore certificate names the signer. Neither shows
that the inputs are true.

\section{The Approval Boundary of an Agent}
\label{sec:boundary}

The agent-facing package, decision-control, evaluates a proposal that a host
supplies. It calls no model, authenticates no one, and its actions only update
a local SQLite ticket table.

\emph{Verdict order and the snapshot guard.} A frozen policy routes a
proposal through eight checks in a fixed order. Four hard constraints (wrong
ticket, unregistered action, a value off the allowlist, no change) give
\code{DENY} before the probability or the refusal is read. A refusal, or a
missing or low probability, gives \code{ABSTAIN}; a value on the review list
gives \code{REVIEW}, however high the probability; otherwise \code{ALLOW}.
At execution, a ticket that has moved from the frozen snapshot gives
\code{STALE} instead of an action, so an approval covers only that snapshot.

\emph{Approval and separation of duties.} A \code{REVIEW} decision needs a
reviewer from the frozen list who is not the proposer. Replay applies the
rule to the exported file: a record edited to name the proposer as reviewer
fails with exit \code{1} even when re-hashed (four tampered vectors). The
rule compares labels: an editor who also renames the proposer passes once
re-hashed, and so does one who names an unlisted reviewer and adds that
name to the frozen list. So does a record
rewritten as schema 2, which has no proposer field. This is general: the
record names the schema version it is replayed under, so every defence a
later version added (the proposer rule, duplicate-key rejection, strict
reading of numbers) is optional for an editor unless the consumer pins a
minimum version outside the file, which no verifier offers, or requires a
signature by a key the editor does not hold. Even a signature does not show that two people were involved;
that needs an identity layer
\citep{south2025delegation,kasselman2026aims}.

\emph{An external decision, bound to the whole proposal.} An OPA decision-log
entry \citep{opa2026decisionlogs} with its Rego modules, or a Cedar
authorization \citep{cutler2024cedar} with its policies and entities, can be
frozen in the record. The frozen input must equal the one derived from the
record's complete proposal, ticket snapshot and proposer: an early Cedar
request left out the model, question version, probability, ticket revision
and non-target fields, so one authorization was accepted for different
proposals. The
binding is one-way; nothing requires a frozen decision: an editor who
deletes a frozen \code{DENY}, records the built-in \code{ALLOW} and re-hashes
passes, even under \code{--require-reevaluation}. Without its engine on the
PATH, replay checks the policy digest-only and exits \code{0}
(\code{2} under that flag).

\emph{A framework's approval interrupt.} The Model Context Protocol says
there ``SHOULD always be a human in the loop with the ability to deny tool
invocations'', asks clients to log tool use for audit, and defines no record
of the approval \citep{mcp2026spec}. A
framework's approval interrupt saves the run state and resumes with an answer
\citep{langchain2026interrupts,openai2026agentshitl}; that state can hold the
call, the answer and a name the caller supplies, but neither the frozen rules
the answer was checked against nor a form a third party can re-check. Our LangGraph example maps an interrupt onto a
record that replays (Appendix~\ref{app:langgraph}).

\section{Evaluation}
\label{sec:evaluation}

\emph{Corpus and editor.} The corpus is the three packages' conformance
vectors: 185 (56 valid, 64 tampered, 65 invalid), the valid ones in twelve
record types and schema versions, shown in eleven rows. Run as black-box
subprocesses on a PATH without OPA, Cedar or \code{cosign}, the verifiers
return each vector's expected exit code (\code{1} tampered, \code{2}
invalid) on 185 of 185. The sweep below models one change to a valid record:
one leaf edited, every digest recomputed or left stale. A key holder who
edits one field and re-signs is the first case, since replay's result does
not depend on the signature. Consistent edits of several fields, which pass,
are not measured.

\emph{Baseline.} The baseline does what a consumer with the schemas but no
replaying verifier can do: every declared document validates against its
JSON Schema, and every digest recomputable from the vector matches. The
schemas are this repository's own. They constrain each field's type, form
and range; none ties a verdict, a lifecycle state or a policy outcome to
other fields. A stricter schema would reject more, leaving replay less to
add: one
\code{if}/\code{then} rule added to record schema 4 rejects the lead example
and accepts every valid v4 record. Of the 64 hand-written tampered vectors
the baseline accepts 36 and the verifiers none (Table~\ref{tab:bykind}), a
count that reflects how many we wrote with consistent digests.

\emph{Mutation sweep.} We edit every JSON leaf of every valid vector once, as
in mutation testing \citep{jia2011mutation}: a number is changed, a string
gets a character appended, a boolean is flipped, a null is replaced
(Appendix~\ref{app:types}). Each of the 4,214 edits runs twice:
\emph{stale}, with every digest left as it was, as an accidental change
would; and \emph{resealed}, with every digest the verifier checks recomputed
in the canonical form the edited schema version requires. The baseline and
the verifier both check each edited record; an edit counts as rejected on a
non-zero exit. Resealed, the baseline rejects 1,104 edits (26.2\%) and the
verifiers 3,466 (82.2\%); 2,375 (56.4\%) only the verifiers reject, and 735
pass both (Table~\ref{tab:sweep}). Stale, the baseline rejects 3,619 of the
4,214 edits (85.9\%) and the verifiers 4,184 (99.3\%); the 565 only the verifiers reject
are all experiment-gate edits outside the input its digest covers, and the
30 that pass both are two version labels.

\emph{What rejects an edit.} A resealed edit is rejected when the edited
record is no longer valid input (exit \code{2}; 717 edits, 605 also rejected
by the schemas) or when it changes a value that replay recomputes or
compares with a copy elsewhere in the record (exit \code{1}; 2,749, 486 also
rejected by the baseline). Recomputation and comparison thus add the 2,263
mismatches the baseline accepts, 53.7\% of the edits. Only a stale digest,
a signature or policy re-evaluation exposes an edit the verifiers accept,
except 13 version relabels that the schemas reject.
By our grouping (Appendix~\ref{app:fields}), the 748
passing edits are 333 inputs whose edited value leaves
every recomputed value unchanged, 295 labels such as a recommendation's model
name or the proposer, 61 edits to frozen external-policy content checked
digest-only, 46 free text and 13 schema versions whose successor reads the
same record. The first kind depends on the operator and the fixtures: 25 of
the 28 action records have probability 0.95 against a minimum of 0.8, which
the minimum's +0.125 edit never crosses, and replay never reads some such inputs, such as a
seed (14 edits). Bar the 61 policy edits, which replay did not re-evaluate,
a passing edit breaks no rule that replay applies. By record type the
verifiers reject from 68.4\% (decision-control record v5, 527 of 770) to
96.8\% of resealed edits; decision-control types hold 646 of the 748
passes, including 261 labels and 307 inputs. Record v5 is lowest because
61 of its 243 passes are these policy edits; with OPA it rejects 535
(69.5\%), above record v4 (69.2\%). Over the five action-record types only
the verifiers reject 464 of 1,212 edits (38.3\%).

\emph{One edit, two records.} Append a character to a model name and reseal.
The Jev answer record rejects it: its verifier re-derives the model
from the stored response. The decision-control
record passes it in every version but in the 4 of 15 v5 vectors whose
frozen OPA input repeats the proposal (a Cedar request keeps the model only
in a digest, which resealing recomputes): that record stores a label in place
of the output behind it. The answer record's protection is single-leaf too:
change the name in both places, re-hash, and it passes. Replay shows that
the two copies agree, not that a provider sent either.

\emph{Re-evaluating a frozen policy.} With OPA 1.21.2 on the verifier's PATH,
8 more resealed edits are rejected (3,474 of 4,214, 82.4\%): edits to the
frozen Rego module and query path in record v5, all of which broke
evaluation. A policy edit that still yields the frozen result passes, and
Cedar, on neither PATH, was checked digest-only throughout.

\emph{What the rates do not show.} One edit per value type, one leaf at a
time, on vectors written by the author of the verifiers: the rates describe
this corpus and operator, not records in general, and not an editor who
changes several fields together or lowers a schema version. The baseline is our own construction and models no receipt
format; no receipt implementation was run. Signatures and latency are not
measured.

\section{Lessons}
\label{sec:lessons}

\emph{One file, two decisions.} One invalid vector has a first
\code{"decision": "HOLD"} member before the real one: a last-wins parser
reads a record that would otherwise verify as \code{SHIP}, a first-wins
parser reads \code{HOLD}. Parsers disagree on such input
\citep{seriot2016json,miller2021json}, and JSON Schema leaves it undefined
\citep{wright2022jsonschema}: read as \code{JSON.parse} does, the baseline
accepts 12 of the 65 invalid vectors instead of 6, all six extra with a
duplicate key. The RFC 8785 schema versions therefore reject duplicate keys,
NaN, Infinity and integers beyond $2^{53}-1$ on reading. Older versions keep
lenient readers, and the editor picks the version: a schema 2 \code{HOLD}
record with an extra first \code{"decision": "SHIP"} verifies, digest
unchanged.

\emph{Fail closed, in checks and in exit codes.} A recurring defect was a
check that passed when its input was missing or invalid: a missing
probability that became 1.0, a JSON \code{null} read as an option not given,
a NaN threshold that compared false with everything. Where exit \code{1}
reports a result (a mismatch, or a failed gate), an uncaught exception, on
which Python exits \code{1}, reports a false one; two verifiers and the
experiment and Jev evaluation gates needed that fix. Three defaults still exit \code{0}
without a full check: an ungated evaluation in decision-control, a frozen
policy checked digest-only, and an invalid signature envelope when none is
required.

\emph{Make digests and floats recomputable elsewhere.} A standard JSON parser
in another language loses the difference between \code{2} and \code{2.0}, so
a digest over Python's \code{json.dumps} needs a reader that keeps number
literals and a port of its float \code{repr}, as our Node checker has; new
schema versions use RFC~8785. Nor is exact float replay portable: five of seven
experiment-gate 0.1.0 records from macOS failed it on Linux, whose math
library differs in the last digit. Outside decision-control, whose
arithmetic is correctly rounded, derived statistics are compared at
relative $10^{-9}$, and a smaller edit passes.

\section{Related Work}
\label{sec:related}

The draft of \citet{farley2026acta} defines a signed receipt per
access-control decision; its receipts ``capture decision metadata, not
request content'', so a verifier learns that an issuer signed a denial, not
that the denial follows from policy and request. The draft of
\citet{msebenzi2026evidence} lets a third party ``recompute every verdict
from signed primitives'', verdicts that are outcomes of verifying a record
(\code{VALID}, \code{INVALID}, \code{UNVERIFIABLE}), not a system's allow or
deny. The verifier of \citet{schrock2026authorization} re-applies separation
of duties with approver-held keys; its required hostile cases include
initiator self-approval, and a separately authored verifier passed 164 of
its conformance vectors from a hash-pinned bundle. AgentBound
\citep{kaul2026agentbound} is nearest to our gate: actions are permitted,
reviewed or denied before execution, and validation ``independently replays
the canonical action against the reconstructed policy models''. Its code and
results are announced, not released; we lack its delegation model.
NovaFabric seals a whole agent run with a trusted timestamp, a Merkle log
and key-separated approval, which we lack, and reports three tamper classes
rejected and 140 single mutations localized \citep{ardebili2026novafabric}.
With one tampered vector \citep{msebenzi2026evidence} and a shared test
suite \citep{farley2026acta}, these are the nearest measurements we found;
none compares replay with digest and schema checks.

By design, an in-toto Simple Verification Result may list the policies used but
leaves ``information for reproducing the verification result'' to additional
provenance attestations \citep{hennen2026svr}.
Our records keep it, and could travel as the payload or subject of an existing envelope, such as a
signed statement in a transparency service \citep{birkholz2026scitt}; we
have not built that. An attestation-aware promotion gate for LLM artifacts
has been proposed \citep{tan2026attesting}; we did not find a promotion
decision over A/B aggregates kept as a recomputable record. Decision
provenance, reviewability and agent visibility asked for decision and
activity logs \citep{singh2019decision,cobbe2021reviewable,chan2024visibility}
and defined no recomputable format or verifier.

\section{Limits and Next Steps}
\label{sec:limitations}

For an LLM agent, seven limits apply. (1) The raw model or tool-call output
behind a proposed action is not in the action record. A chained example puts
an answer record's digest into the model label and prints ``Only this recipe
checks that link. No verifier does''; storing the output is proposed, not
built. (2) Proposer, reviewer, producer and model identities are
caller-asserted, no field separates an agent from the principal it acts for,
and no record authenticates the provider. (3) Execution is local; nothing
shows an effect in an external system. (4) There is one record per decision:
no trajectory or multi-agent record, no hash chain, and nothing shows that
every decision produced a record. (5) Sampled actions (bandit or RL
policies) are not recorded. (6) No record carries a trusted time of the
decision; only decision-control records timestamps, from the local clock.
(7) We report nothing on an agent benchmark such as AgentDojo
\citep{debenedetti2024agentdojo}. On approval binding
(approver-held keys bound to one canonical action,
\citealp{schrock2026authorization}; single-use approvals of the exact bytes
that will run, \citealp{jing2026separation}), on chaining and completeness
\citep{sharif2026aat} and on trusted time \citep{ardebili2026novafabric},
existing work is ahead.

Whoever writes or rewrites a record consistently passes replay, the producer
included: the party that writes the record is the party being audited
\citep{figuera2026notarized}, and agents can tamper with their own traces
\citep{qin2026tamper}. A transparency service does not prevent this
\citep{birkholz2026scitt}; it holds a producer accountable for what it
registered, in an append-only history that every relying party sees alike.
Embedding the inputs makes recomputation possible and exposes them to
whoever holds the record; receipts leave them out on purpose
\citep{farley2026acta}, and we offer no redaction. A human approval step
invites rubber-stamping: one vendor reports that users accept 93\% of its
coding agent's manual permission prompts \citep{hughes2026automode}; a
record shows that an approval was written down, not that the review was
careful. An unaffiliated reproduction and a pilot under a protocol frozen
before any result are planned and not started.

decision as payload. \code{Command(resume=...)} carries the decision, the
reviewer and a note to approve or reject, after the store has checked the
frozen reviewer list and refused the proposer. The end of the review node
exports the record. Only a \code{REVIEW} verdict interrupts.

Two traps were met. A node re-runs from its first line on resume, so a node
that submitted and then interrupted would submit twice: submit and interrupt
are separate nodes. And LangGraph keeps the resume value of a node that
raised and gives it to the next attempt (observed with langgraph 1.2.16), so
a refusal is returned as state, not raised. The example has no model call:
its proposal is a hand-written literal. Thread and checkpoint identifiers go
into the review note, which replay treats as free text.

Three details of the package that Section~\ref{sec:boundary} leaves out or
only counts. The registered actions are \code{reassign_ticket} and
\code{set_ticket_priority}. A built-in verdict and a frozen external verdict
combine by taking the more restrictive one, in the order \code{DENY},
\code{ABSTAIN}, \code{REVIEW}, \code{ALLOW}. And the four self-review
vectors of Section~\ref{sec:boundary} are records v3, v4 and v5 with the
proposer as reviewer and a v4 record with the proposer as the cancelling
reviewer; replay rejects all four with exit \code{1}.

\section{Reproduction}
\label{app:repro}

{\raggedright
The cross-language check and the evaluation run from a checkout of commit
\commitid{b90ebc0}, on the branch that carries this draft. Outside the evaluator, its
packages, schemas, vectors and Node checker equal those of commit
\commitid{1626280} of the repository (\repourl); the schemas and vectors are
also served at \siteurl.
\par}

{\small
\begin{verbatim}
cd scripts/conformance && npm ci
node verify.mjs  # schemas and digests
V=/tmp/venv; W=../../ai-workflows
python3 -m venv $V  # Python 3.11+
$V/bin/pip install $W/experiment-gate \
  $W/jev-decision $W/decision-control
npm run evaluate -- --bin $V/bin \
  --out /tmp/eval-out --latency-runs 0 \
  --compare-inherit-path
cd ../.. && make records-chain \
  DEMO_OUT=/abs/new/dir
\end{verbatim}
}

{\raggedright
The second line runs the Node checker: it validates every declared document
against its schema, recomputes every digest of the valid vectors, and prints
\code{conformance OK: 3 manifests, 185 vectors, 319 checks, 0 failures}. The
evaluation writes \code{results.json} and \code{RESULTS.md}; with latency
measurement off, as here, its output is deterministic. It runs each edited
record through the baseline and the verifier. It gives the verifiers a PATH
of the virtual environment's \code{bin}, \code{/usr/bin} and \code{/bin}, so
frozen OPA and Cedar decisions are checked digest-only, and
\code{--compare-inherit-path} repeats the sweep with the caller's PATH; the
82.4\% figure needs \code{opa} 1.21.2 there. The last command, which runs
\code{python3} (3.11 or newer) from the source tree, writes and verifies one
record with each package. It builds a decision-control proposal from a Jev
answer, puts \code{jev:} followed by that answer's record digest in the
proposal's model label, and prints the limit quoted in
Section~\ref{sec:limitations}.
\par}
